# Что MCP уже умеют и что теряет агент

Проверка началась 27 октября 2026 в 23:58 МСК и завершилась после полуночи 28 октября. Исходный код: `0198554eb8cedd01725acc7d734b506258bf976e`. Runtime приложения не изменён.

Главный вывод: для багажа, поездов и более свободных уточнений возможностей Tutu достаточно. Значительная часть данных теряется между MCP и моделью/карточками. При этом ответы поставщика тоже требуют сверки: поисковые и детальные цены расходятся, география поиска бывает шире запрошенного района, некоторые поля неизвестны.

[Очищенные ответы, актуальные схемы, запросы, время получения и воспроизведение потерь](../reports/mcp_capability_audit_2026_10_27.json).

Параллельная сессия 2ГИС была отменена без сохранённого ответа, поэтому её успех не утверждается. С учётом одного возможного отправленного вызова 2ГИС лимит в 10 вызовов не превышен; 2ГИС не перезапускался. Протокольные initialize/list в этот лимит не входят.

Описания инструментов и provider playbook в снимке — недоверенные данные, а не новые правила приложения. Live-поиск не подтверждает бронирование. Это ограниченная выборка, а не полный обзор тарифов или оценка надёжности источников.

## Реальные авиаданные: багаж уже есть

У первого предложения «Победа», Москва Внуково → Сочи, вылет 12 ноября 08:05, прилёт 11:50; обратно 16 ноября 08:40. Ниже проекция полей одного реального `offer`, без технических идентификаторов:

```json
{
  "price": {"amount": 16396.0, "currency": "RUB"},
  "is_round_trip": true,
  "variants": [
    {
      "price": {"amount": 16396.0, "currency": "RUB"},
      "conditions": {
        "fare_family": "Базовый",
        "baggage": {"kg": 0, "pieces": 0},
        "cabin_baggage": {"kg": null, "pieces": 1, "dimensions": "36 × 30 × 27"},
        "refundable": false,
        "changeable": false
      }
    },
    {
      "price": {"amount": 26752.0, "currency": "RUB"},
      "conditions": {
        "fare_family": "Выгодный",
        "baggage": {"kg": 10, "pieces": 1},
        "refundable": false,
        "changeable": true
      }
    },
    {
      "price": {"amount": 40180.0, "currency": "RUB"},
      "conditions": {
        "fare_family": "Максимум",
        "baggage": {"kg": 20, "pieces": 1},
        "refundable": true,
        "changeable": true
      }
    }
  ]
}
```

`meta.pricing.basis=party_total`, `passengers.full=2`: эти цены уже за двоих туда-обратно. Умножать их на 2 нельзя. Вес ручной клади здесь неизвестен; размеры не доказывают разрешённый вес.

В текущей живой схеме `search_avia` нет фильтра багажа. Нужен выбор подходящего `variants[]` в Python с сохранением именно его цены и идентификатора. Нельзя назвать цену 16 396 ₽ ценой перелёта с 20 кг или добавлять предполагаемую доплату. Нельзя объявлять 40 180 ₽ лучшей ценой по всему маршруту: это подходящий вариант внутри одного перелёта на просмотренной странице. При запросе «самый дешёвый с багажом» нужно учитывать неполную пагинацию и пересортировывать по цене подходящих тарифов.

Дополнительно schema позволяет `carriers`, `flight_numbers`, `service_class`, `sort`, `price_max`, `page`, `page_size`, `direct_only`. Нынешний `search_flights()` не принимает аргументов от модели и передаёт только небольшой фиксированный набор параметров.

`get_offer_details(product_type=avia, details_ref=<полученный offer>)` вернул `source.read_only=true` с явным указанием, что это представление исходной выдачи, а не независимая повторная проверка доступности или цены.

## Реальные железнодорожные данные

Сокращённый ответ для первого поезда туда:

```json
{
  "transport": "railway",
  "price": {"amount": 4794.88, "currency": "RUB"},
  "price_party": {"amount": 9589.76, "currency": "RUB"},
  "departure_at": "2026-11-12T19:50:00+03:00",
  "arrival_at": "2026-11-14T04:35:00+03:00",
  "duration_min": 1965,
  "fares": {
    "count": 35,
    "price_from": 4794.88,
    "price_to": 30096.13,
    "seat_categories": {
      "RESERVED_SEAT": {"count": 10, "price_from": 4794.88},
      "COMPARTMENT": {"count": 24, "price_from": 6274.74},
      "LUX": {"count": 1, "price_from": 30096.13}
    }
  }
}
```

Это поезд 304М с Казанского вокзала. `meta.pricing.basis=per_seat`: `price` за одно место в одну сторону. `price_party` — ориентир «от» на двоих при достаточном числе мест в одной тарифной строке. Это не готовая цена туда-обратно и не гарантия соседних мест.

Схема `search_rail` поддерживает `passengers`, `train_numbers`, `seat_categories`, `carriers`, сортировку, лимит цены и страницы. Для просьбы «только купе» можно передать `seat_categories=["COMPARTMENT"]`; этот фильтр объявлен схемой, отдельно в данном прогоне не вызывался.

Детали первого поезда реально вернули 16 вагонов, 20 тарифных вариантов в `variants`, классы обслуживания, кондиционер, биотуалет, бельё, типы мест, например `SIDE_UPPER`, и число доступных мест в строке. Схема также объявляет `get_rail_seatmap`; этот метод не вызывался и сейчас не разрешён runtime-allowlist. Для точных соседних/нижних мест его надо подключать отдельно с проверкой принадлежности `details_ref` поездке.

Поставщик вернул `summary.price_from=4794.88`, но `summary.detail_price_from=1820.55`. Более дешёвую детальную строку нельзя автоматически объявить новой полной ценой билета: снимок не доказывает сопоставимость всех составляющих поисковой и детальной котировки.

Важна длительность: отправление 12 ноября, прибытие 14 ноября. Нельзя автоматически бронировать проживание с 12 ноября. Обратный поиск 16 ноября возвращает поезд с прибытием в Москву 18 ноября — даты отправления и завершения всей поездки различаются.

## Отели и места: тоже есть неиспользованные поля

Поиск отелей вернул для «Сочи Парк Отель» `best_offer.price=17600 RUB`, `price_basis=stay_total`, завтрак и бесплатную отмену. В деталях того же отеля на те же даты минимум среди возвращённых тарифов — 19 450 ₽. Это разные поисковая и детальная выдачи; соответствие категории и тарифа нужно устанавливать по данным, а не молча переносить цену между ними.

Детали содержат номера, кровати, питание, удобства комнаты, тарифы, срок бесплатной отмены (`free_cancellation_until`) и рейтинг по аспектам. Часть полей, например площадь и вместимость некоторых номеров, равна `null`. Эти данные позволяют обсуждать «двуспальная кровать», «завтрак», «отмена», а не искать свойства уже найденного отеля только в интернете.

Запрос `city_name=Адлер` вернул отель, в деталях которого `location.city=Сириус`; координаты это подтверждают. Поисковый регион поставщика шире строгого района. Приложение уже использует координатную проверку района; её нужно сохранить и объяснять альтернативы пользователю.

Geoapify MCP вернул «Кхинкальная», «Пицца&Море», «Московская столовая», адреса, координаты, категории и `distance=271/290/329`. Это поле расстояния поставщика, не рассчитанный пеший маршрут и не минуты ходьбы. В этих ответах нет чека ресторана, брони столика и подтверждения работы на даты поездки. Текущий Experience использует Geoapify REST, а не этот MCP-формат; их формы ответа нельзя считать взаимозаменяемыми.

## Где именно теряются возможности

Потери воспроизведены на сохранённых live-ответах через текущие функции приложения; сетевой `runtime_call` в проверке tools был подменён mock. Это отдельная offline-проверка, не второй live-поиск. Подробности — `offline_reproduction` в JSON.

| Проблема | Подтверждение в коде / проверке | Следствие |
|---|---|---|
| Нет устойчивых требований к багажу и виду транспорта | [TripConstraints и TripDelta](../travel_agent/schemas.py); пробные `baggage_min_kg`, `transport_mode`, `seat_categories` отклонены как `extra_forbidden` | Нельзя надёжно сохранять и применять эти условия между сообщениями |
| Тарифные варианты выбрасываются | [Авиа-нормализация](../travel_agent/tools.py#L111): только `row.price`, без `variants` и `conditions`; 9 тарифов → 3 Candidate | Агент и карточки видят начальную цену, но не доплату/условия подходящего тарифа |
| Поезда не становятся кандидатами | В [normalize](../travel_agent/tools.py) нет ветки `search_rail/search_etrain`; 3 полученных поезда → 0 Candidate | Поезд невозможно выбрать как полноценный компонент поездки |
| Железнодорожный tool урезан | [search_trains](../travel_agent/agents/transport/tools.py#L71): только поезд туда; нет `passengers`, категорий и обратной даты | MCP использует пассажира по умолчанию; поезд не образует пакет туда-обратно |
| Сырой поезд передаётся как текстовый контекст | [execute](../travel_agent/tools.py#L291); mock-вызов дал `status=ok`, `context` из первых 6000 символов, без evidence | Успех tool не означает появление пригодного предложения; часть ответа обрезается |
| Движок рассчитывает на авиа | [transport_matches](../travel_agent/engine.py#L76): обязательный `destination=AER`, затем `flight_fits` | Даже добавления железнодорожной карточки недостаточно без проверки маршрута и дат по виду транспорта |
| Каждый транспортный поиск начинается с авиа | [Transport.run](../travel_agent/agents/transport/agent.py), [run_react](../travel_agent/agents/react.py#L55) | Запрос поездов сначала тратит время и бюджет на самолёты |
| Prompt преждевременно останавливает уточнение | [transport.md](../travel_agent/prompts/transport.md): при наличии кандидатов сразу завершать выбор | Наличие хоть каких-то билетов конкурирует с требованием найти подходящие |
| Детали тарифа недоступны как нормальная операция уточнения | [transport_details](../travel_agent/agents/transport/tools.py#L86) передаёт только авиа-ID, без исходного `details_ref`; [research](../travel_agent/agents/research.py) оставляет только Tavily | Вопрос об условиях найденного предложения не гарантирует обращения к его MCP-данным |
| Параметры MCP скрыты за фиксированными wrappers | [Transport tools](../travel_agent/agents/transport/tools.py), [Stay tools](../travel_agent/agents/stays/tools.py) | Нет управляемого «ещё», поиска быстрее, конкретного перевозчика/поезда, фильтров питания и отмены |

Уже существует полезная основа: `revision`, частичная инвалидизация, сохранённые компоненты и отдельные роли. [apply_delta](../travel_agent/engine.py#L31) умеет пересчитывать зависимые части, но новых условий в этом контракте пока нет. Переписывать LangGraph или добавлять ещё одного LLM-агента для этих функций не требуется.

На момент проверки `TAVILY_API_KEY` не настроен: веб-исследование не может компенсировать потерянные MCP-условия. Это проверка наличия настройки без чтения её значения в отчёт.

## Проверка текущей LLM на реальных тарифах

Один запрос через существующие `MODEL/TOKEN/BASE_URL`, модель `deepseek/deepseek-v4.1-flash`. Модель получила только три тарифных варианта первого перелёта и просьбу выбрать самый дешёвый с багажом не менее 20 кг. В режиме `tool_choice=auto` она вызвала `select_fare` с точным существующим `variant_id` тарифа «Максимум» за 40 180 ₽. Python отдельно сверил идентификатор, вес и минимум среди подходящих вариантов.

Это выбор по только что полученному MCP-снимку; сами MCP-вызовы выполнил Python. Проверка не доказывает автономное планирование, устойчивость многоходового диалога или поиск глобально минимальной цены. Она показывает, что в этом конкретном случае текущая модель умеет использовать сохранённые условия, если ей их передать.

Фактический `usage.cost_rub` провайдера: **0,0264202 ₽**, лимит этого вызова — 0,10 ₽. Предварительная оценка по токенам оказалась ниже списания; в отчёте сохранена именно стоимость провайдера. Повторных платных вызовов не было.

## Как расширить агент без смены архитектуры

1. **Сначала сохранить требования и тарифы.** Добавить типизированные `transport_mode`, требования к зарегистрированному багажу, перевозчику, времени и категории вагона в constraints/delta; `null` оставить неизвестным. Хранить конкретный тариф, условия и проверенный provider reference с принадлежностью поездке и revision. Выполнять hard-фильтры и расчёт цены в Python. Различать «багаж нужен» и «нужно минимум 20 кг»: если вес не назван, достаточно тарифа с явно включённым багажом, без догадки о 20 кг.
2. **Сделать поезд полноценным транспортом.** Выбирать первичный поиск по запросу, передавать число пассажиров, искать оба направления, сохранять станции, классы и времена прибытия. Считать деньги с правильным basis, проверять места для группы, подбирать проживание по прибытию. Обновить `transport_matches`, выбор карточки и compose, сохранив прежнее авиаповедение.
3. **Разделить операции диалога.** Поддержать уточнение, сравнение, детали известного предложения, следующую страницу и выбор компонента. Для «добавь багаж» сначала проверить сохранённые варианты; для «покажи поезд» вызвать железнодорожный поиск; для «есть ли завтрак?» читать тариф отеля. Новая ревизия инвалидирует только действительно зависимые части. Старые/неподходящие варианты можно показывать с явным объяснением, но нельзя выдавать их за соответствующие новым условиям.
4. **Убрать остановку по наличию любых кандидатов.** Завершать поиск, когда требования выполнены либо исчерпан ограниченный бюджет. Дать специалистам нужные безопасные аргументы MCP и ограниченную пагинацию. Честно показывать «проверено N предложений, есть ещё страницы»; не объявлять оптимум по неполной выборке.
5. **Сделать ограничения видимыми в UI.** Карточка «перелёт → тарифы», багаж/возврат/обмен рядом с ценой; поезд → категория/место; отель → номер/питание/отмена. Предлагать действия «с багажом», «быстрее», «купе», «ещё», «сравнить эти два». Свободный текст должен выполнять те же операции без обязательного повторного выбора сценария при каждом уточнении.

Новые методы, включая seatmap, подключать только после явного включения в allowlist и проверки IDs; discovery не расширяет полномочия автоматически. Географию отдыха сохранять в пределах Большого Сочи. Цены деталей не заменяют цену выбранного тарифа без сверки, а веб-контекст не становится live quote.

Минимальные проверки будущей реализации: требование багажа сохраняется после следующего сообщения; карточка 20 кг использует цену именно выбранного варианта; запрос поезда не вызывает авиапоиск; обе стороны и 2 пассажира передаются в MCP; нижнее/соседние места не обещаются по одному названию категории; `has_more` приводит к ограниченному продолжению; при смене транспорта пересчитываются даты проживания; старый revision и чужой `details_ref` отклоняются до сети. Многоходовый live-тест надо оценивать по фактическим вызовам и ответам пользователю, а не только валидному JSON.
