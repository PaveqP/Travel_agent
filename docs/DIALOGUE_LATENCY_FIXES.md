# Область запроса и задержки диалога

Дата: 29 октября 2026. Изучены два последних пользовательских диалога в локальном PostgreSQL и журнал работавшего backend. Истории, идентификаторы пользователей и сырые ответы поставщиков в этот документ не копируются.

## Подтверждённые причины

- В самостоятельном запросе проживания `focus` остался пустым. Граф автоматически добавил отсутствующие компоненты, потребовал город отправления, запустил Transport и Experience и собрал пакет вместо отелей. В сохранённых результатах этого диалога — 117 транспортных кандидатов и 19 кандидатов проживания.
- Вопрос об обосновании рекомендации закончился `planner outcome=ValidationError`, поле `reply`, тип `string_too_long`. Ограничение в 1000 символов применялось и к содержательному объяснению; пользователь получил общий отказ ещё до ответа.
- Планирование и извлечение параметров выполнялись двумя последовательными LLM-вызовами. Для объяснения готовых вариантов отдельно вызывался Presenter. Специалисты продолжали поиск до лимита, хотя факты уже были получены. Во втором диалоге накопились 103 транспортных кандидата, 60 отелей и 24 места; все три специалиста достигли лимита.
- Кэш MCP учитывал только завершённые вызовы. Одновременные одинаковые запросы могли уходить в сеть дважды. То же происходило при геокодировании одного города несколькими инструментами.

## Изменения

1. Supervisor явно определяет область по предмету запроса. Запрос отелей означает `stays`, запрос билетов — `transport`; слово «только» не требуется. Scope сохраняется при уточнениях. Наличие старого пакета больше не отменяет явно указанную область. При одной задаче начального поиска граф также выводит scope из роли. Для проживания город отправления не обязателен; отдельные даты заселения/выезда поддерживаются. Полная поездка включается через `focus=trip`.
2. В автономном workflow решение, параметры и область извлекаются одним структурированным LLM-вызовом. В промпт перенесены правила извлечения дат, бюджета, мягких пожеланий и восстановления вводных из истории. Проверка контракта и одна попытка исправить формат сохранены.
3. Для `answer` Supervisor возвращает готовый ответ непосредственно. Поиск и Presenter не запускаются. Контекст включает координаты, адреса, условия, реальные даты, стоимость и места программы. Неизвестное время трансферов должно оставаться неизвестным. Если ответ не заполнен, остаётся прежний путь Presenter. Допустимый размер `reply` увеличен до 12000 символов, а промпт требует краткого ответа. Изменения из `patch` у справочного ответа не применяются.
4. Добавлены блокировки на одинаковый MCP-запрос и геокодирование внутри делегации. Разные запросы продолжают работать параллельно. Автоповтор после MCP timeout убран; один повтор после сетевой ошибки сохранён. ReAct ограничен четырьмя модельными шагами и восемью tool calls; существующий финализатор и частичные результаты сохранены. Промпты требуют завершать поиск после достаточной выборки и проверять детали выбранных кандидатов параллельно.
5. При явно названном отеле другой отель не может незаметно стать подходящим предложением. Убран оставшийся фильтр карточек, связывавший любой горнолыжный запрос только с Красной Поляной. Роли, доступ к данным, модель, endpoint и ключи не менялись.
6. В безопасный журнал LLM добавлены длительность и исход без содержимого запросов и ответов.

## Проверки и ограничения

Добавлены 11 регрессионных проверок: HTTP-подбор проживания без транспорта, сохранение scope, явное расширение до пакета, вывод scope из одной роли, сужение существующего пакета, объяснение длиннее прежнего лимита за один вызов, независимые даты заселения, сохранение частичного статуса, объединение параллельных дублей MCP/геокодирования отсутствие автоповтора timeout и независимость самостоятельных дат от старого ночного перелёта. Два последних механизма проверяются отдельными тестами.

Перед правками общий Python suite имел 35 failures и 41 error после предыдущего расширения географии. Тестовые запросы с сочинскими fixtures теперь явно называют Сочи, вместо зависимости от удалённого направления по умолчанию. Устаревшие ожидания запрета Москвы, автоматического сочинского календаря, жёстких горных дней и карты только Сочи приведены к уже принятому контракту России. Проверки безопасности, источников, денежных расчётов и изоляции сохранены.

Проверяются полный offline suite, frontend tests, production build и запуск локального сервера. Платные LLM/MCP-вызовы при исправлении не выполняются. Уменьшение числа вызовов подтверждается offline-тестами; ускорение в секундах на реальном провайдере пока не измерено. Более короткий ReAct-цикл может оставить больше явно обозначенных пробелов при медленных источниках: приложение сохраняет полученные факты, вместо обещания полного результата.

Для ручной проверки откройте http://localhost:8000 и обновите страницу. Новый запрос отелей лучше проверить в новой поездке, поскольку старый диалог уже содержит лишний пакет. Объяснение первого и второго варианта можно повторить в существующем диалоге. Данные старых поездок не удаляются и не переписываются.

Результат проверок: 205 Python-тестов, 8 пропущены из-за отсутствия опциональных условий, ошибок нет; 17 frontend-тестов прошли. Production build, compileall, проверка diff и поиск секретов в изменённых файлах успешны. После перезапуска `/health`, `/` и `/api/destinations` отвечают HTTP 200; PostgreSQL подключён (`persistent=true`).
