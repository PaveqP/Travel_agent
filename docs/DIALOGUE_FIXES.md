# Исправления по пользовательским диалогам

Проверены две последние сохранённые поездки в PostgreSQL: горнолыжная поездка с просьбами о багаже, бане и жалобе, затем запрос готового тура на двоих 10–20 декабря до 200 тысяч рублей. Личные данные, checkpoint и полные диалоги в Git не добавлялись.

При диагностике работающий Docker-backend оказался старее перенесённой архитектуры: у его `create_app` отсутствовал параметр `autonomous`, ответы требовали последовательного выбора сценария, билетов и отеля. В последней поездке все явно сообщённые параметры остались пустыми. Город отправления не был указан и в профиле — это единственное необходимое уточнение, остальные данные должны сохраняться.

Изменения:

- При достаточных вводных граф сразу собирает пакет и выбирает рекомендованный вариант для обсуждения. Формат отдыха не блокирует поиск. Точные даты приоритетны над разговорным числом дней.
- Извлечение требований видит предыдущие сообщения пользователя и предложенный patch. Пустой ответ извлечения не стирает заполненные параметры.
- Все тарифные `variants` авиапредложения сохраняются со своей ценой и `conditions`, включая килограммы багажа, ручную кладь, возвратность и обмен. Для чтения деталей сохраняется исходная ссылка на предложение; цена тарифа с багажом не подменяется базовой.
- Изменение багажа или билета сохраняет выбранный отель и программу; изменение отеля возвращает целый пакет с сохранёнными билетами. Предыдущие предложения доступны специалисту для повторного использования.
- Experience получает текущую программу и последнее сообщение. Правка одного дня не требует раскладывать всю программу заново. Посещение одного горнолыжного курорта в несколько дней разрешено; Python больше не удаляет такие повторения или явно предложенные перемещения между районами одного дня.
- Сравнения и письмо-жалоба обрабатываются как ответы на конкретную просьбу. Старые веб-источники не делают обязательными цитаты в письме, а шаблон поддержки не перехватывает автономный диалог.
- Убрано принудительное отключение инструментов после двух шагов. Модель может уточнить детали и исправить структурированный ответ в общем бюджете. Провайдерам доступны параметры класса перелёта, перевозчика, сортировки, удобств отеля и питания; произвольные пожелания сохраняются в `requirements`.

Изоляция владельцев и ролей, проверка принадлежности ID, source-based цены и денежный basis, отклонение запоздалых результатов и явное подтверждение имитации покупки сохранены. Они не определяют текст ответа или последовательность пользовательских действий.

Регрессии находятся в [test_dialogue_changes.py](../tests/test_dialogue_changes.py). Проверяются настоящие граф, API, LangChain ReAct и обработка ответов поставщика с mock LLM/HTTP/MCP. Отдельный PostgreSQL-режим использует `TRAVEL_TEST_DATABASE_URL` и тестовую БД, без доступа к рабочим поездкам. Платные live-вызовы для этих проверок не нужны.

После обновления кода работающий backend нужно пересобрать: `docker compose up -d --build app`. Проверка наличия новой архитектуры без LLM-запросов:

```bash
docker compose exec -T app python -c "import inspect; from travel_agent.api import create_app; print(inspect.signature(create_app).parameters['autonomous'].default)"
```

Ожидаемый результат — `True`. PostgreSQL-том, аккаунты и история при пересборке сохраняются.
