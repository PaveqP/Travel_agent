Корреляция wire → runtime result временная по роли/tool/безопасным параметрам, а не по сквозному MCP ID; исходные runtime events сохранены в trace, неоднозначность не считается доказательством точной связи. REST http_ok означает HTTP-успех, а не доказательство валидного продукта; реальный tool outcome отдельно в trace.

## Проблемы и невыполненные требования

- Первое полное сообщение с датами, бюджетом и горным днём получило повторный вопрос «Когда хотите поехать?». В typed tasks/reply даты и бюджет есть, но patch их не содержит; итоговый TripConstraints теряет эти вводные.
- Потребовалось повторить уже сообщённые факты в следующем пользовательском ходе.
- Во всех пяти вариантах ноль горных дней при mountain_days=1; обязательная программа не собрана после встроенного repair.
- Главный результат кейса — оформленная simulated покупка — не достигнут, POST bookings получил 409. Не снимали ограничение горного дня ради успешного оформления.
- Ответ вводит внутренние option/hotel IDs в пользовательский текст; допущение о шаговой доступности набережной не подтверждено конкретным расстоянием.

## Рекомендации

- Согласовать planner.patch и отдельное извлечение TripDelta; проверять, что явные факты не пропадают между reply/tasks и constraints.
- Добавить offline regression на этот фактический диалог, не меняя критерии успешности.
- В repair Experience сначала завершать days по сохранённым подтверждённым ID, а не расширять каталог POI.
- Согласовать доступность оформления и объяснение причины блокировки; сохранить проверки mountain_days и бюджета.
