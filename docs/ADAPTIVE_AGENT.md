# Адаптивный агент без потерь ответов поставщика (историческая реализация)

Эта реализация заменена архитектурой из `KilArtur/Flinters`, коммит `f1dc3bf`. Действующие режим, контракты и ограничения описаны в [автономном планировании](AUTONOMOUS_PLANNING.md). Ниже сохранён исторический отчёт; он не описывает текущий runtime.

Изменение от 28 октября 2026. Исходная диагностика и реальные примеры MCP сохранены в [аудите](MCP_CAPABILITY_AUDIT.md).

## Передача данных

Из runtime удалены `normalize`, `search_dates`, `transport_matches`, `stay_matches`, `usable` и `flight_fits`. Python больше не превращает ответы поставщика в ограниченный набор кандидатов и не отсекает их по цене, району, названию, датам, виду транспорта или полноте пакета. Убраны принудительный первый авиапоиск, программные резервные поиски, сортировка по дешевизне, ограничения в 30 карточек, 100 сохранённых кандидатов и пять вариантов сборки.

Каждый вызов сохраняет `SourceObservation`: идентификатор, роль, revision, аргументы, ограничения поездки на момент запроса, статус, источник, полный `data` и исходный MCP envelope в `response`. Неизвестные вложенные поля, все тарифы, метаданные, пояснения ошибок и длинные тексты остаются доступны. Ошибка модели, timeout, изменение пожеланий и неудачное обновление не удаляют предыдущие ответы. Те же данные получает Supervisor, специалист следующего хода и модель ответа на вопросы.

Модель выбирает источник, параметры, направление, класс, страницы, порядок поиска, сравнение и представление карточек. `requirements` хранит произвольные условия пользователя без заранее заданного перечня сценариев. Структурированные поля включают фактические возраста детей, вид транспорта и класс. Они сохраняются при последующих изменениях. В промпты не добавлен набор тестовых диалогов: конкретные пользовательские случаи находятся в тестах.

`present_offers` проверяет сформированные моделью карточки. `field_refs` указывают на точные поля сохранённых ответов; `price_parts` позволяют проверить сумму нескольких исходных котировок через Decimal. Ошибочную карточку можно исправить, не повторяя сетевой поиск. Полный ответ поставщика остаётся в состоянии независимо от публикации карточек. Неизвестное свойство не превращается в подтверждённое.

## Что умеют инструменты

- Авиа: даты и аэропорты, взрослые/дети/младенцы, `service_class`, перевозчики, номера рейсов, сортировка, страницы и доступные фильтры поставщика. Локального ценового потолка нет.
- Железная дорога: оба направления отдельными вызовами, реальный размер группы, категории вагонов, номера поездов, сортировка и страницы; детали и карта мест используют оригинальный принадлежащий поездке `details_ref`.
- Автобусы: отдельный инструмент поиска и безопасное чтение деталей.
- Отели: фактические возраста детей, даты, питание, условия отмены, удобства объекта/номера, тип размещения, страницы, полные детали и отзывы.
- Справочные вопросы могут обращаться к MCP-деталям своей роли, а не только к Tavily. Данные предыдущего исследования доступны в последующих ходах.

Возрастные группы для avia переводятся только в формат контракта поставщика: младенцы младше двух лет, дети от двух до одиннадцати, пассажиры от двенадцати в счётчике взрослых. Исходные возраста сохраняются. Нельзя обещать детскую скидку на поезд, если источник её не подтвердил.

Для особых услуг агент сохраняет требование и проверяет доступные источники. Если поставщик не подтвердил перевозку животного на конкретном рейсе, это остаётся неподтверждённым условием, а не причиной выбросить ответ или объявить услугу согласованной. Без `TAVILY_API_KEY` веб-источник недоступен; отсутствие ключа сохраняется отдельным исходом.

React показывает состав семьи и универсальные подписи прибытия/отправления. Железнодорожный вариант больше не получает жёстко заданный аэропорт AER.

## Сохранённые проверки

Изоляция ролей, разрешённые методы, принадлежность IDs/references поездке, проверка JSON Schema, URL, revision и подтверждение имитации покупки сохранены. Новые методы включены в allowlist явно; discovery не расширяет права. Значения ключей не попадают в observations.

Свежесть котировки и совместимость выбранных компонентов проверяются перед имитацией оформления; эти проверки не скрывают исходные предложения. Кэш не становится live quote. Изменение состава группы требует соответствующей котировки. Исходная валютная цена сохраняется, но не суммируется с RUB без курса и не выдаётся за нулевую стоимость. Превышение пользовательского бюджета показывается предупреждением, а не исключением предложения.

Один ход делегирует одну роль. Специалист ограничен восемью вызовами модели, десятью tools и восемью сетевыми операциями, общим deadline. Реальных checkout, платежей и передачи паспортов нет. Хранилище и переменные `MODEL`, `TOKEN`, `BASE_URL` не менялись.

## Проверка поведения

[Исторические тесты адаптивности](https://github.com/ostrovok-hackathon-2026/flinters/blob/297cc4e/tests/test_adaptive_agent.py) запускали настоящий ReAct с mock LLM/MCP, проверяя вызовы, аргументы, сохранённые данные и итоговые цены:

| Случай | Проверяемое поведение |
|---|---|
| Зарегистрированный багаж | Выбрана цена конкретного подходящего варианта, остальные варианты сохранены |
| Ребёнок и младенец | В avia переданы разные счётчики, в отель — исходные возраста, состав сохранён в карточке |
| Животное | Требование и условия источника сохранены; неизвестное согласование не объявлено подтверждённым |
| Поезд | Вызваны оба направления с нужной группой и категорией, авиапоиск не вызван, сумма собрана из двух котировок |
| Бизнес-класс и дорогой перелёт | Нужный класс передан в MCP, дорогой тариф остаётся доступен даже выше бюджета |
| Последующее уточнение | Старые полные ответы и более 100 карточек сохраняются после ошибки обновления |

Дополнительно проверены принадлежность seatmap reference, сохранение всего MCP envelope при бизнес-ошибке, понятная ошибка неверных аргументов до `tools/call`, запрет утверждать класс только по аргументам запроса и редактирование секрета без обрезки остальных полей. Сквозной тест FastAPI → StateGraph → create_agent → mock MCP проходит выбор компонентов, пересборку и идемпотентную имитацию покупки.

Команды:

```bash
.venv/bin/python -m unittest discover -s tests -v
cd frontend
npm test
npm run build
```

После пополнения баланса выполнена проверка с настроенной `deepseek/deepseek-v4.1-flash` через Polza. [Исходные результаты и полные новые ответы MCP](../reports/adaptive_agent_llm_validation_2026_10_28.json).

Live-проверка выявила и помогла исправить потерю необязательных полей Supervisor, неверный формат класса, слишком короткий LLM timeout и преждевременное завершение до валидации карточки. Карточки теперь публикуются только через `present_offers` с обратной связью; список пропущенных ссылок возвращается целиком. Динамические `facts` и `field_refs` принимают также JSON-строки, чтобы строгая схема tools не запрещала произвольные ключи; после валидации они остаются словарями без потерь.

Для Polza отключено длительное рассуждение через документированный `reasoning: {effort: "none"}`: [формат провайдера](https://polza.ai/use-cases/seo-content). `MODEL`, `TOKEN`, `BASE_URL` и `.env` не менялись. Таймаут LLM согласован с настроенным deadline. Полный live-тест тарифа выполнялся с deadline 180 секунд и лимитом 4096 токенов; штатные значения приложения — 90 секунд и 8192 токена для специалиста.

Итог: unittest — 122 теста, 8 пропущены, ошибок нет; frontend — 5 тестов и успешная production-сборка. По полученным usage-ответам суммарно списано 8,42139420 RUB, включая неудачные диагностические попытки; для запросов, оборванных по timeout, провайдер не вернул usage. Исторический тариф не является текущим наличием. Оформление, платежи и передача документов не выполнялись.
