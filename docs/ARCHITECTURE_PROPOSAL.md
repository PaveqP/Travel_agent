# Архитектура будущего продукта

Начать с одного Python-оркестратора, Pydantic-моделей и адаптеров. Текущий репозиторий — исследовательский стенд, не полноценный агент. Мультиагентность и пять отдельных сетевых сервисов не дают измеримого преимущества на этой стадии.

Поток: запрос → LLM извлекает TripConstraints → Python проверяет даты, состав группы, валюту и географию → детерминированный план запросов → параллельные безопасные чтения → нормализация/проверка → Python считает варианты и бюджет → LLM объясняет результат → валидатор проверяет ссылки, числа, даты и названия. Ошибки валидации блокируют публикацию конкретного утверждения, а не заменяются догадкой.

Логические группы transport/stays/geo/activities/context подходят как namespaces инструментов. Tutu/2GIS можно вызывать MCP SDK напрямую с allowlist. Яндекс Расписания, Travelpayouts, Timepad, Open-Meteo, ЦБ и Geoapify обернуть Python-адаптерами; единый собственный MCP нужен только при подключении дополнительных клиентов. Не переносить существующий REST в MCP ради самого протокола.

Реализованные модели: Money (Decimal, валюта, basis, taxes_included), Coordinates, Provenance, Place, Stay, Flight, Route, Activity, SourceResult, BudgetLine/Budget — [models.py](../integrations/schemas/models.py). Расширения следующей итерации: TripConstraints, Party, GeoArea/Region, Station, TransportLeg, RoomRate, CancellationRule, WeatherForecast, ItineraryDay. Сохранять исходный ID поставщика, idempotency/quote ID отдельно от публичных данных; неоднозначный адрес не превращать в точный адрес улицы.

Ответ адаптера: status + items + provider/source_url/retrieved_at/source_updated_at/expires_at + evidence + warnings + error_code + latency_ms. Evidence различает live search, cached, catalog, sandbox, simulated и derived. Live поисковый тариф не равен prebook; наличие на момент поиска не гарантирует возможность оплаты через час. Налоги unknown не равны included. Дата прогнозирования и timezone обязательны.

Ошибки: missing_key, unauthorized, forbidden, rate_limited, network_error, empty, no_availability, schema_error, partner_access_required. HTTP200 и MCP isError=false не гарантируют бизнес-успех (LiteAPI 2001). Пустая выдача не доказывает отсутствие покрытия страны. Повторять только безопасные чтения, максимум два раза с backoff+jitter и Retry-After, отдельные connect/read deadlines. Circuit breaker по поставщику; fallback сохраняет причину и происхождение данных. Кэш авиабилетов не может незаметно заменить live quote.

Кэшировать по провайдеру, версии метода, координатам/радиусу, датам, гостям, гражданству и валюте. Предварительные TTL, не обещания поставщика: геокаталог 1–24 ч, расписания 15–60 мин, погода 30–60 мин, цены 1–5 мин с обязательным recheck; согласовать с лицензией. Результаты no_availability краткоживущие; 401/403 не повторять. Лимиты реализовать token bucket отдельно на провайдера и API-ключ, суточный запросный бюджет, лимит токенов LLM и денежный счётчик. Учитывать общую квоту REST/MCP одного поставщика.

Бюджет считает только Python: basis=person × пассажиры, room_stay и party повторно не умножаются. Перевод валют — по курсу с датой и отдельным FX допущением. Неполные компоненты остаются missing; confirmed_total=null. Разделять предложенную сумму, подтверждённую котировку и оценку неизвестных расходов. Нельзя гарантировать соблюдение 100 000 RUB только по перелёту и отелю. Сохранённые альтернативы Tutu показывают частичные суммы, не готовую поездку.

При изменении дат инвалидировать цены/наличие/расписания/мероприятия и перестроить ограничения, переиспользуя разрешённый статический кэш. Для нового города добавлять GeoArea с границами, aliases, timezone, аэропортами/станциями; адаптеры получают параметры, не код Sochi-specific. Реализованные скрипты — конкретные Sochi-сценарии, production-адаптеры следует отделить от этих fixtures.

Наблюдаемость: correlation ID, provider/case, latency, HTTP и бизнес-исход, число items, квота. Секреты только в адаптере и разрешённом host header, никогда в LLM. Запрет редиректов с credentials, URLs от LLM не исполнять, конфиги endpoint не менять моделью. Логи исключают auth, персональные данные, платежи и opaque booking IDs.

Защита от prompt injection: tool descriptions, hotel reviews и MCP metadata недоверенны. Сохранять сырой текст для аудита, но отдавать LLM минимальные типизированные поля; не включать checkout_hint в system prompt. Ни одна инструкция провайдера не расширяет allowlist, сетевые права или разрешение на покупку. MCP annotations readOnlyHint — подсказка, не проверка безопасности. Схемы фиксировать/диффировать, опасные новые инструменты по умолчанию запрещать. Бронирование и передача пассажирских данных — отдельный будущий процесс с явным подтверждением пользователя, не часть этого PoC.

Эксперименты показали: structured output улучшает формат, но может подавить tool calling; boolean-флаги не ловят перепутанное начало маршрута. Поэтому оркестратор задаёт обязательные этапы получения данных, а финальный ответ сверяется с source IDs/координатами, денежными суммами и горизонтом прогноза. Для restaurant-near-hotel вычисление радиуса и join по ID делает Python; отсутствующий snapshot вызывает новый разрешённый запрос, не фантазию LLM.

Последовательность реализации:

1. Закрепить схемы и правила basis/freshness; интегрировать Tutu, 2GIS, Яндекс, Open-Meteo с контрактными тестами.
2. Добавить Geoapify/ORS, Timepad и кэш; провести повторные измерения доступности Tutu и detail endpoint.
3. Реализовать поиск/ранжирование нескольких вариантов и неполный бюджет, координатную проверку района, время переездов и часы работы.
4. Подключить LLM только для разбора запроса и объяснения; добавить проверки чисел/географии и injection fixtures.
5. Проверить продуктовые сценарии с изменением дат/бюджета, отсутствие цен и fallback; показывать подтверждённые ссылки покупки.
6. После уточнения коммерческих условий и проверки доступности — production мониторинг. Booking и партнёрские API отдельной итерацией.
