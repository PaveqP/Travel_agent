# Проверка последних сессий: 28 октября 2026

Проверены последние четыре сохранённые поездки из PostgreSQL и checkpoints графа,
а также логи работающего приложения. Одна поездка пустая; три содержат диалог.
Платные LLM/API smoke-проверки не выполнялись. Содержимое диалогов и идентификаторы
пользователей в репозиторий не добавлены.

## Что привело к сбоям

- В последней поездке были известны месяц, двое взрослых и город, но отсутствовали
  точные даты и длительность. `search_dates` использовал стандартные семь ночей,
  а граф считал месяц достаточным для поиска. После выбора первого пакета граф
  записывал его даты как ограничения пользователя. Теперь автономный граф требует
  даты либо окно с длительностью; предварительная сборка не сужает исходное окно.
- Transport получил и авиа, и ЖД. Проживание оказалось совместимо с поздним
  прибытием поезда, поэтому авиа не вошло в пакеты. Проверка считала достаточным
  любой совместимый транспорт. Теперь Stay получает интервалы проживания разных
  способов проезда; отсутствие отеля для другого найденного вида транспорта
  вызывает адресную проверку. При смене транспорта старые производные даты отеля
  сбрасываются. Несовместимые даты не исправляются выдуманной котировкой.
- До исправления программы были доступны пять пакетов. В следующем круге граф
  ограничивал транспорт и отель автоматически рекомендованными ID, оставляя один
  пакет. Теперь ограничения сохранённого выбора относятся к редактируемым
  компонентам пользовательского хода, а не к техническому кругу исправлений.
  Разные рейсы с одним отелем также могут быть отдельными вариантами.
- Experience нашёл десятки мест, но не вернул календарь. В логах есть остановки по
  лимиту tools и ошибки завершения LLM. Теперь часть общего deadline отведена на
  отдельное завершение `SpecialistSelection` по компактным фактам без нового
  поиска. Источники и ID проверяются после завершения. Если точечная правка
  провалилась, проверенная прежняя программа сохраняется с явным предупреждением.
- При отсутствии полного пакета UI показывал найденные билеты только списком.
  Теперь свежие совместимые компоненты получают карточки и выбор. Выбранный билет
  задаёт фактические даты зависимых частей. Самостоятельный поиск транспорта
  поддерживает свой focus, как поиск проживания.
- В более ранних сессиях также встречались неявная замена длительности стандартной
  и маршрутизация изменения тарифа как справочного вопроса. Унифицированные
  промпты разграничивают изменение условий, исследование, ответ и выбор, сохраняют
  вводные и свободные требования без примеров отдельных запросов.

## Откуда мог взяться вход на 90 тысяч токенов

В последней сессии checkpoint содержал 100 транспортных кандидатов. Старый JSON
для `saved_evidence`, уже без `provider_details`, занимал **243 638 символов**.
До этого 83 кандидата занимали около 200 тысяч символов. Каждый следующий
`search_flights` возвращал весь накопленный evidence, а ReAct сохранял предыдущие
ответы tools в истории. При повторном круге список снова попадал в начальный
контекст. На размер влияли длинные ID, ссылки, повторяющиеся поля и варианты
тарифов. Сохранение только последних 100 записей дополнительно могло вытеснить
котировки исходных дат.

Теперь начальный контекст ограничен 24 краткими кандидатами, выдача tools —
20 новыми кандидатами, `search_flights` возвращает данные своего запроса.
`ContextEditingMiddleware` очищает старые ответы tools при превышении порога,
оставляя два последних. Полное evidence сохраняется отдельно для проверки фактов,
выбора и деталей; оно не обрезается по принципу «последние 100».

На том же сохранённом наборе новый начальный список занимает **29 214 символов**:
на **88% меньше**. Это размер списка кандидатов, не обещание снижения всей оплаты
на 88%. Точный состав конкретного оплаченного запроса на 90 тысяч токенов
восстановить нельзя: прежние production-логи не содержали usage каждого вызова.
Добавлены логи request/thread/role, приблизительного размера входа и фактических
input/output/total tokens из ответа SDK, включая вызовы, завершённые до ошибки
следующего шага. Сырые prompts, ответы и секреты не логируются.

## UI

- Обработка привязана к ID поездки: можно открыть новый диалог, пока предыдущий
  запрос завершается; ответ остаётся в своей поездке.
- Предварительно показанное сообщение удаляется сразу после ответа и не выводится
  повторно, если оно уже пришло из сохранённой истории.
- Поздний GET не перезаписывает более новый ответ POST. Открытие новой поездки
  очищает текущий экран и состояние формы.
- В пустом диалоге нет карты. История доступна только в «Мои поездки»;
  дублирующий блок «Мои планы» удалён.

## Воспроизводимые проверки

```bash
.venv/bin/python -m unittest discover -s tests -v
npm --prefix frontend test
npm --prefix frontend run test:browser
npm --prefix frontend run build
```

Для браузерных тестов после `npm ci` при необходимости установите локальный браузер:
`cd frontend && npx playwright install chromium`.
Браузерные тесты поднимают локальный Vite и подменяют API, внешние запросы
блокируются. Проверяются создание второй поездки во время первого запроса,
возврат и перезагрузка без дублей, поздний GET и пустой экран.
PostgreSQL-проверки включаются через `TRAVEL_TEST_DATABASE_URL` на отдельной
тестовой базе, без изменений данных пользовательских поездок.

Результат проверки: 189 unittest без ошибок; в стандартном прогоне пропущено
11 проверок, с отдельной PostgreSQL — только 3 Linux PTY-проверки на macOS.
Также прошли 17 frontend unit-тестов, 5 браузерных проверок и production-сборка.
