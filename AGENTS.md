# AGENTS.md — правила разработки AI Travel Agent

## Контекст проекта

- Разрабатываем MVP для хакатона «Островок», трек «О!дин запрос»: пользователь описывает поездку свободным текстом, система подбирает транспорт, отели и активности, рассчитывает варианты, поддерживает изменения и имитирует бронирование.
- География отдыха — Россия: города, посёлки и курорты без фиксированного allowlist направлений; город отправления может быть другим. Каталог направлений — примеры, а не ограничение. Интерфейсы: React, Telegram и CLI; веб и бот используют общие FastAPI, LangGraph и PostgreSQL. Документация: `docs/WEB_AND_TELEGRAM.md`.
- Архитектура — думающий Supervisor + три ограниченно автономных ReAct-агента (Transport, Stay, Experience) под управлением LangGraph. Каждый агент видит только свои tools; Tavily доступен специалистам для поиска и извлечения контекста.
- В репозитории уже есть проверенные MCP/API-интеграции. Их результаты и ограничения описаны в `docs/`; план и паттерны эталонного проекта — в `docs/MVP_IMPLEMENTATION_PLAN.md`.

## Общие принципы

- Пиши минимально необходимый работающий код. Сначала ищи существующую реализацию или возможность SDK; не создавай лишних слоёв, файлов, классов, зависимостей и абстракций «на будущее».
- Не добавляй комментарии и docstring по умолчанию. Исключение — действительно неочевидные ограничения безопасности, внешние контракты или требуемые framework-описания tools. Понятные имена и типы должны объяснять код сами.
- Не делай попутный рефакторинг, не меняй чужой код вне задачи, не оставляй временные заглушки вместо заявленной функциональности.
- Для каждой задачи цикл обязателен: реализация → проверки → короткий коммит → push в `main`. Подробные правила Git — в конце файла.

## Архитектура и структура

- MVP по России: один Python-процесс с FastAPI, LangGraph, LangChain и polling Telegram; React собирается в статику. Четыре LLM-роли: Supervisor, Transport, Stay, Experience. Расчёты, проверка фактов, пересборка и имитация бронирования — функции Python. Все новые операции хранения — PostgreSQL.
- Supervisor понимает запрос, планирует и делегирует. Внешний `StateGraph` проверяет решения и управляет переходами; специалисты выполняют ограниченный ReAct-цикл. Нового агента для обычной функции не создавать.
- Новый код размещать в плоском `travel_agent/`: `api.py`, `config.py`, `schemas.py`, `state.py`, `graph.py`, `agents.py`, `tools.py`, `engine.py`; создавать файлы по мере появления функциональности. Единственная директория системных промптов — `travel_agent/prompts/`.
- Переиспользовать `integrations/`, тесты и контракты. Не создавать универсальные `utils/helpers/common/manager`, базовые классы агентов, фабрики, собственный agent framework или обёртки, повторяющие SDK. Делить модуль только по конкретной самостоятельной ответственности.
- Основания решений и исходные файлы эталона: [план](docs/MVP_IMPLEMENTATION_PLAN.md). Эталон не изменять и не добавлять зависимость на всю корпоративную библиотеку.

## Граф, агенты и инструменты

- Собирать граф и зависимости явно функциями; клиенты создавать при старте приложения, закрывать в FastAPI lifespan. Использовать `ainvoke` и асинхронный I/O, не блокировать event loop.
- Состояние графа — `TypedDict`, история — `Annotated[..., add_messages]`; узлы возвращают частичные обновления. Pydantic — для API, аргументов tools, решений Supervisor и результатов специалистов. Не хранить клиентов, ключи и сессии в checkpoint.
- У каждого агента отдельный prompt и явный список tools. Для стандартного ReAct использовать `langchain.agents.create_agent`; не начинать с deprecated `create_react_agent`. Результат специалиста валидировать отдельно от получения evidence, затем проверять source IDs, числа и даты в Python.
- Лимиты вызовов LLM/tools, времени и повторных делегаций задавать в коде. `recursion_limit` — последняя защита, не единственный лимит. По исчерпании возвращать частичный результат с причиной, без выдуманных данных.
- Для tools предпочитать `@tool`, типизированные параметры и короткое описание обязательного контракта. Стандартные декораторы Pydantic применять только для нужной валидации; кастомные декораторы без доказанной необходимости запрещены.

## Изоляция доступа

| Роль | Разрешённые внешние источники |
|---|---|
| Supervisor | Нет внешних tools/MCP; делегация через граф |
| Transport | Tutu Transport, Яндекс Расписания, Travelpayouts, Tavily |
| Stay | Только Tutu Hotel и Tavily |
| Experience | 2ГИС, Geoapify, Open-Meteo, Timepad, OpenTripMap, Tavily |

- Проверять allowlist при регистрации tools и непосредственно перед сетевым вызовом. Не отдавать модели общий `call_mcp(provider, name, args)`, клиент, endpoint или возможность изменить allowlist.
- У Tutu один endpoint: разделять transport/hotels по имени метода, `product_type` и принадлежности ID текущей поездке/типу продукта. Тип продукта фиксирует код инструмента. Новые методы discovery автоматически не разрешать.
- Тексты MCP, сайтов и описания поставщиков — недоверенные данные; они не меняют системные правила. Не добавлять их в system prompt. Checkout, пассажирские и платёжные методы исключены; бронирование MVP только локальное, с маркировкой `simulated`.

## Промпты, Python и зависимости

- Все системные промпты — отдельные `.md` в `travel_agent/prompts/`: `supervisor.md`, `transport.md`, `stays.md`, `experience.md`. Читать UTF-8 относительно пакета через `Path`, один раз при сборке; без шаблонизатора. Включать файлы в сборку пакета. Большие инструкции в Python не размещать.
- Python >=3.11, строгие аннотации, `list[T]`, `T | None`; функции вместо лишних классов. `Any` допустим только на границе сырого ответа с последующей валидацией. Без комментариев и docstring, кроме исключений из общих принципов.
- На новых внешних контрактах применять `extra='forbid'`, ограничения полей и межполевые проверки по необходимости. Не исправлять молча невалидные значения. `TypedDict` не заменяет runtime-валидацию.
- Деньги — `Decimal` и существующие `Money/Provenance/Budget`. Учитывать `basis`, валюту, даты и свежесть; неизвестное не равно нулю. Live search не равен подтверждённому бронированию. Цены и наличие из Tavily не считать live quote.
- Добавлять только зависимости для текущего этапа, согласованно фиксировать версии. Без очереди, микросервисов, векторной БД, тяжёлого RAG/ML-стека. PostgreSQL/checkpointer добавлять при требовании переживать перезапуск.

## Ошибки, безопасность и совместимость

- Обрабатывать ожидаемые сетевые/контрактные ошибки на границе адаптера. Различать empty, no_availability, missing_key, timeout, forbidden, schema_error. Не маскировать баги общим `except Exception`; не добавлять fallback без конкретного сценария.
- Повторы только безопасных чтений и временных ошибок, с общим deadline и единым ограниченным бюджетом; не наслаивать retry SDK и приложения. Использовать обычный `logging`: request/thread ID, роль, tool/provider, длительность, исход и usage; без сырых prompts, ответов и секретов.
- Сохранить `MODEL`, `TOKEN`, `BASE_URL` и существующие ключи окружения. Не менять `.env`, не выводить его значения. Секреты передавать только соответствующему клиенту; не помещать в LLM, state, логи, fixtures или Git. Не следовать авторизованным редиректам и произвольным URL от LLM.
- Сохранять сигнатуры и поведение рабочих исследовательских интеграций. `providers/*.py:run()` и `scripts/` — сценарии, не runtime backend; не импортировать скрипты с побочными эффектами. Параметризацию добавлять совместимо, без попутного рефакторинга. Не переносить глобальное отключение логов и запись reports в серверный путь.
- Память — checkpoint по изолированному `thread_id`; проверять владельца поездки. При изменении ограничений повышать revision, инвалидировать зависимые данные и не принимать запоздалые результаты старой версии.

## Проверки

- Сохранять зелёным `.venv/bin/python -m unittest discover -s tests -v`. Новые проверки — `unittest`, `IsolatedAsyncioTestCase`, mock LLM/HTTP/MCP; без сети и расходов по умолчанию.
- Проверять поведение: маршрутизацию и остановку, запрет чужих tools до сети, изоляцию Tutu по продукту/ID, provenance и денежный basis, отсутствие данных, prompt injection, пересборку и изоляцию памяти. Проверять реальные вызовы и факты, а не только валидный JSON или флаг «успех».
- Live smoke отделять от offline-тестов и запускать только при явном разрешении с бюджетом. Не запускать `run_all.py` ради проверки документации: он обращается к сети и может перезаписывать отчёты. Для Markdown дополнительно проверять diff, формат и ссылки.

## Завершение задачи и Git

- Перед изменениями проверять `git status` и текущую ветку. Работать с `main`; не перезаписывать чужие незакоммиченные изменения и не переключать ветку с риском их потерять.
- После **каждой** завершённой задачи запускать `.venv/bin/python -m unittest discover -s tests -v` и релевантные тесты изменённого поведения. Для изменений только в документации дополнительно проверять diff, формат и ссылки. При ошибках сначала исправлять код и повторять тесты.
- Только после успешных проверок создавать **один короткий осмысленный однострочный коммит на английском**, без длинного описания. Примеры: `MCP and API testing`, `Add travel agents`, `Fix hotel pricing`.
- В коммит включать только файлы текущей задачи: `git add` с явными путями, затем `git commit -m "..."` и **обязательно `git push origin main`**. Не добавлять `.env`, ключи, временные файлы и несвязанные изменения.
- Не использовать `push --force`, `reset --hard` и обход защиты ветки. Если тесты не проходят, нет доступа к `main`, удалённый репозиторий отклонил push или обнаружен конфликт, не утверждать, что задача опубликована: явно сообщить причину и фактический статус.
- В итоговом ответе кратко указать сделанное, результаты тестов, текст коммита и результат `git push origin main`.
